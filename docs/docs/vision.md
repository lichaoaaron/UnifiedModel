# MModel 产品定位

## 产品定义

在当前这版方案中，MModel 被定义为一个偏独立的运维语义层与故障调查平台。

MModel 不承担底层日志、指标、Trace 的采集、存储或基础展示职责，而是在这些运行时数据之上构建统一的对象语义、对象关系、证据聚合和调查上下文，让运维人员、Web、CLI、Agent 与大模型围绕同一套运行时对象模型协同工作。

## 为什么要做

现代 IT 系统的调查过程通常分散在多个数据入口、多个对象体系和多套查询方式中。用户往往能看到日志、指标和 Trace，却无法快速回答以下问题：

- 当前异常到底对应哪个运行对象。
- 这个对象依赖谁、被谁依赖、影响会向哪里传播。
- 某个故障时刻真实存在的运行拓扑是什么。
- 与该对象相关的证据应该从哪里查看。
- Agent 应该基于什么结构化上下文给出可信的诊断。

MModel 的目标是把复杂系统调查从“面向数据源”转为“面向对象、关系与证据”。

## 产品目标

- 建立统一的运行时对象模型。
- 将日志、指标、Trace、事件等数据组织为以 Entity 为中心的数据模型。
- 为 Web、CLI、Agent 和大模型提供统一的数据访问与调查接口。
- 降低运维人员理解复杂系统和定位故障的成本。

## 核心价值

- 先看到对象，再看到证据。
- 先理解关系，再判断影响。
- 先获得结构化上下文，再执行 AI 诊断。
- 先沉淀统一能力，再对接不同平台。

## 产品边界

在当前方案设想中，MModel 主要负责：

- Runtime Entity Model
- Entity / Relation / Topology
- Evidence 聚合与关联
- Historical Runtime
- Investigation Timeline
- Query API
- Diagnosis API
- 面向 Web、CLI、SDK、MCP 的统一能力输出

宿主平台主要负责：

- 登录与会话
- 菜单入口与导航
- 时间范围同步
- 上下文传递与跳转
- 原始数据视图承接

## 设计原则

- 当前文档倾向于将 MModel 作为相对独立的产品能力进行设计，而不是直接按单一 Dashboard 插件来约束其边界。
- 当前文档建议将核心业务能力优先沉淀在 MModel Core 中，以便后续支持多平台接入。
- 平台集成层在本稿中主要承担接入职责，是否进一步承载更多能力，可结合阶段目标再讨论。
- 结合目前的分工假设，Copilot 可以消费 MModel 能力；同时，MModel 侧仍保留对象、证据、拓扑和调查语义相关的核心表达。
